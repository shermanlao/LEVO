# Product datasheets

Catalog **Datasheet** generates a LEVO PDF from the product row in SQLite. There are no static files under `frontend/public/datasheets/` for individual products. The same row also drives the **Installation** PDF.

## Public URL

This route is rewritten from Next.js (`frontend/next.config.ts`) to Express.

Example: `/api/datasheets/lx-ad10104` → `DL00001-datasheet.pdf` when that product’s `product_code` is `DL00001`.

The product page buttons (`ProductDetails`) and the series product list (`ProductList`) use `getDatasheetUrl(slug)` in `frontend/src/lib/sqlite-api.ts`, which returns this path. The PDF opens in a new tab (`Content-Disposition: inline`).

A **custom** datasheet for a series configuration (not a listed SKU) is `GET /api/series/:slug/datasheet` with variant query params. See [series-configurator.md](series-configurator.md).

A **family** datasheet for the whole series (filters ignored) is `GET /api/series/:slug/family-datasheet` → `{series-name}-family-datasheet.pdf` (for example `EcoPro-family-datasheet.pdf`; falls back to the model code, then the slug). The series page title row opens it (`getSeriesFamilyDatasheetUrl(slug)`). Generated by `buildFamilyDatasheetPdf` in [`datasheetPdf.ts`](../backend-server/src/lib/datasheetPdf.ts):

- Same LEVO header/footer chrome as the SKU datasheet; header heading is **Family Datasheet**. Page breaks are natural (not a fixed page count)
- **Hero:** 1:1 `featured_image_datasheet` crop (then source, then `featured_image`, then first size-pack Main A) on the left; type name, `{series}, {product_code}`, key-fact chips (min–max wattage, source lumen, CCT, beam, IP, CRI from unique `series_options`), and the marketing `description`. When a `description_phrase` exists it is filled with those family ranges, not a single SKU
- **Badges:** IP / warranty / voltage (and extra series icons) from `/admin/variant-options`, same as before
- **Physical / Technical** tables from unique option values (and size-pack dimensions / cut-out). Several values join (`2700K, 3000K, 4000K`); wattage, lumen, efficacy, and beam print as ranges. Empty `series.specifications` is not used as the only spec block; extra keys there print as **Notes** under the tables
- **SKU coding** as a column grid (not compact wrapped lines): one cell per SKU segment, width fitted to that header / code / option list (not a fixed 4-column slot). Cells wrap to the next row when the next cell plus a hyphen would exceed the content width. Each cell has a muted header, a light grey bar with left/right inset and vertically centered code text, and `code - label` rows in regular weight on one line (PDFKit is not allowed to wrap at the hyphen). A hyphen sits between neighbouring grey bars, vertically centered on the bar, including a trailing hyphen when the next segment wraps to the following line. The bar shows the code when that segment has a single value (blank when there are several choices). A column with more than five options lists in two sub-columns. Codes are not bold. The model column is the series `product_code` only (no series name). Other columns are omitted when the series has only one real option for that kind (for example Trim `WH` or CRI `90`), so the coding key matches the printed SKU. Columns follow physical → electrical → optic → control (Finish, Trim, Reflector, Wattage, CCT, Beam, CRI, Control). If a variant-options `code` is empty, a compact fallback is used (`15` → `15W`, `2700K` → `27K`, `24°` → `24D`, `White` → `WH`, `Opal Diffuser` → `OD`, `0-10V` → `010`, `Non-dimmable` → `ND`). Empty segments are omitted. A muted example SKU (first code from each column, hyphen-joined) sits under the grid
- **Sizes:** each series size option (not leftover product packs) in a compact column — heading, cut-out, then the size drawing in the photo slot (no Main A/B on this page). Under the drawing is a small `Power | Source | System` table from wattage options (`formatSpecValue` + `lm`), width matched to the drawing, not the full page. Lumen lives on wattage options, so every size card repeats the same table. There is no “Available options” dump under each size, and no cartesian SKU rows
- **Colour options:** labeled **Finish** / **Trim** / **Reflector** chip groups from appearance kinds (`colour` / `trim_color` / `reflector_finish`). A group is omitted when every value is empty or `N/A`. Each group’s width is the title or the chip columns (column at least 58pt, wider when the label needs one line). Groups that fit sit on one row with a gap; a group that would overflow wraps to the next row (chips also wrap when that group is wider than the content area). Chips are small circles with the name centered under the circle; mapped colours come from `finishSwatchColors`, White is stroked black, and unmapped values (for example Opal Diffuser) still get an outlined circle and label
- **Appearance:** current Finish × Trim × Reflector combo photos from `series_appearance_photos` print after the chips (`familyAppearancePhotoRows` — leftover photos from tags that are no longer selected are omitted). The **APPEARANCE** heading is kept with the first photo row so it does not sit alone at the bottom of a page. Photos sit close under the heading (top-aligned in the slot); extra space sits before the next section
- **Photometry:** one stamped polar PNG per **power × beam** pair (`familyPolarCombos`), not a full SKU cartesian and not one plot per beam only. Labels look like `10W · 24°`. Intensities are the library cone for that beam, scaled by that wattage’s **source lumen** (`series_options.lumen` → LDT lamp flux) into **cd** (`cd/klm × source_lm / 1000`). System lumen is printed on the size card only; it does not scale the plot. Plots that share a beam use one ring scale (the max peak in that beam) so a lower wattage cannot look stronger just because its own auto-scale was smaller. A failed combo is skipped (same warn pattern as the SKU datasheet). The **PHOTOMETRY** heading stays with the first plot row and uses the same tight heading-to-image / wider section gap as Appearance
- Footer QR opens the public series page with no query params. Installation details live on the separate family Installation PDF, not on this sheet

Button `helpKey`: `catalog.family_datasheet.download`.

## Installation PDF

Series pages use one **Installation** PDF for the whole family (`GET /api/series/:slug/installation` → `{product_code}-installation.pdf`, `getSeriesInstallationUrl(slug)`). Query params are ignored. The button sits next to **Family Datasheet** on the series title row (`SeriesFamilyTitle`). `ProductSkuDialog` opens the same family file. Table rows keep **Datasheet** and **LDT** only.

Generated by `buildFamilyInstallationPdf` in [`datasheetPdf.ts`](../backend-server/src/lib/datasheetPdf.ts):

- Header and footer on every page (LEVO wordmark and “Installation”, plus `site_contacts` footer). Footer QR opens the public series page with no query params.
- Title `{series}, {product_code}`
- Size drawings from each size pack (`size_image`) when present
- Installation specification table from unique `INSTALLATION_FIELDS` values (mounting, sizes, cutholes, IP, input, driver, control) — same join/range rules as the family datasheet
- Notes built from those same field values

A leftover SKU-row route still exists: `GET /api/datasheets/:slug/installation` (`buildInstallationPdf`, `getInstallationUrl(slug)`) for a single product row.

Button `helpKey`: `catalog.installation.download` (seeded in `ensureDefaults.ts`).

Catalog action labels are **Datasheet**, **Installation**, and **LDT** — each with an icon; the word “Download” is not shown on the buttons. On `/products/[type]/[series]`, **Family Datasheet** and **Installation** sit on the title row; each table row has **Datasheet** and **LDT**.

## Layout

Generated by [`backend-server/src/lib/datasheetPdf.ts`](../backend-server/src/lib/datasheetPdf.ts) to match the LEVO product-specification sheet:

- **Every page** of every generated PDF (datasheet and installation) gets the same chrome: LEVO wordmark (`frontend/public/images/levo-logo-mark.png`) and document heading at the top, company/contact/version/disclaimer footer at the bottom, each on a light grey band (`#E5E7EB`, matching `.site-chrome` on the website) with a full-width rule. Footer text and the QR sit 36pt from the page edges (same inset as the left and right content margin); the grey band still runs to the left, right, and bottom edges. Chrome is painted on `pageAdded` inside the margin band so it cannot create a blank first page (PDFKit otherwise page-breaks when footer text sits below `maxY`).
- Header heading is “Datasheet” on SKU datasheets, “Family Datasheet” on family sheets, and “Installation” on installation sheets, **18pt bold**, matching the LEVO wordmark size on the right of the grey header band.
- Content (series title, photos) starts **26pt** below the header band so the title is not tight against the grey bar.
- Left: product photo, size drawing, and photometric polar in a **square** slot, with no grey fill or border. The photo slot is always reserved (blank if the file is missing). Size drawing comes from the matching size pack. The polar plot is rendered from the LDT library for the selected beam and series shape (see [photometric-ldt.md](photometric-ldt.md)) — a stored size-pack `photometric_image` is not used for series combinations. Below the photos: compact **labels** (32pt black squares, wrapping to extra rows), matching `/admin/variant-options`. IP / warranty / voltage fill from the product spec (with `variant_option_catalog.label_image` when that option has artwork). Upload URLs stored as `/uploads/…` resolve from `frontend/public/images/products/` (the same folder Express serves for `/uploads`). Extra squares come from stored **series** picks (`product_series.datasheet_labels`) of Variant catalog extras (`kind` `datasheet_label`). Staff create those icons on `/admin/variant-options` and click tags on `/admin/product-series/[id]`. `/admin/product-types` does not show or add labels. Empty spec slots stay auto-drawn from the values.
- Right: black title `{series}, {product_code}`, then the hyphen-joined model code with **no** `SKU` prefix, then intro (filled `description_phrase` when the series has one, otherwise the marketing description, otherwise an auto-built LED sentence), then Physical / Technical tables (labels and values black, zebra rows, label and value **optically centered** on Helvetica cap-height `718/1000`, not the full line box with unused descender space). Extra space sits between the title, code, description, and the two specification sections. Ordering-code squares are **not** on this sheet (the unique SKU is already printed under the title). The family coding key lives on the family datasheet instead.
- Footer: company line from `site_contacts` (address, brand slogan, email, phone, optional website), year, a **QR code** on the right, and the technical-tolerance `datasheet_disclaimer` (rated values at 25°C, ±10% flux/load, ±150 K CCT, no liability for typographical errors). Staff can edit that text at `/admin/settings`. The QR (and click target) opens the public series page with this combination’s query params plus `preview=1`, so the table is filtered to that variant and the preview dialog opens. The origin is **Website** in `/admin/settings` when that is a public URL, then `SITE_ORIGIN` / `NEXT_PUBLIC_SITE_URL` on the production host, otherwise `http://localhost:3000`. The URL is written into the PDF when it is generated; older files are not rewritten.

Partner fields (`vendor_code`, `vendor_model`, `external_id`, LightX URLs) are omitted. A series named LightX is not used in the title; the public product name is shown instead.

Datasheet table labels live in `DATASHEET_PHYSICAL_FIELDS` / `DATASHEET_TECHNICAL_FIELDS` in [`productSpecs.ts`](../backend-server/src/lib/productSpecs.ts) (`Source Lumen` / `System Lumen`). The catalog page uses `TECHNICAL_SPEC_FIELDS` in [`product-specs.ts`](../backend-server/src/lib/shared/product-specs.ts) (`Source Lumen` / `System Lumens`).
